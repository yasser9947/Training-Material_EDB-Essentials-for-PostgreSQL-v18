لماذا VACUUM ضروري؟Why is VACUUM Essential?

PostgreSQL يستخدم MVCC — عند UPDATE أو DELETE، الصف القديم لا يُحذف فوراً. بدل ذلك يُترك كـ "dead tuple" حتى يأتي VACUUM ليحرر مساحته.

PostgreSQL uses MVCC — on UPDATE/DELETE, the old row is not immediately removed. It becomes a "dead tuple" until VACUUM reclaims the space.

مثال — دورة حياة UPDATE:Example — UPDATE lifecycle:

  1. TX1 يقرأ صف "Alice, 30"
  2. TX1 reads row "Alice, 30"
  3. TX2 يُحدّث "Alice, 31" — ينشئ نسخة جديدة، القديمة تُحدد كـ dead
  4. TX2 updates to "Alice, 31" — creates new version, old marked dead
  5. TX1 ما زال يرى "Alice, 30" (consistent snapshot) ✓
  6. TX1 still sees "Alice, 30" (consistent snapshot) ✓
  7. بعد انتهاء TX1، الصف القديم أصبح garbage لكن لا يُحذف
  8. After TX1 ends, old row becomes garbage but isn't deleted
  9. VACUUM لاحقاً يحرر المساحة
  10. VACUUM later reclaims the space

أنواع VACUUM الثلاثةThree Types of VACUUM

VACUUM

الأساسي — يحرر dead tuples، يعمل online (لا يقفل).

Standard — reclaims dead tuples, online (no lock).

✓ آمن في الإنتاج
✓ Safe in production
لا يقلل حجم الملف — المساحة تُستخدم لصفوف جديدة
Doesn't shrink file — space reused for new rows

VACUUM FULL

يعيد كتابة الجدول كاملاً — يحرر المساحة للـ OS.

Rewrites whole table — returns space to OS.

✗ يقفل الجدول (ACCESS EXCLUSIVE)
✗ Locks table (ACCESS EXCLUSIVE)
✗ يحتاج مساحة إضافية (2×)
✗ Needs extra space (2×)

VACUUM FREEZE

يجمّد الصفوف لمنع wraparound.

Freezes rows to prevent wraparound.

⚡ يعمل تلقائياً عند الحاجة
⚡ Runs automatically when needed

أوامر الصيانةMaintenance Commands

-- Standard VACUUM (non-blocking)
VACUUM;                            -- entire database
VACUUM customers;                  -- specific table
VACUUM (VERBOSE) customers;        -- show details

-- VACUUM + ANALYZE together (common)
VACUUM ANALYZE orders;

-- VACUUM FULL (locks! use offline hours)
VACUUM FULL orders;

-- VACUUM with options (PG12+)
VACUUM (VERBOSE, ANALYZE, PARALLEL 4) big_table;

-- Check bloat percentage
SELECT schemaname, relname,
       n_live_tup, n_dead_tup,
       ROUND(100.0 * n_dead_tup / NULLIF(n_live_tup + n_dead_tup, 0), 2) AS dead_pct,
       last_vacuum, last_autovacuum
FROM pg_stat_user_tables
WHERE n_dead_tup > 1000
ORDER BY dead_pct DESC NULLS LAST
LIMIT 20;

-- ANALYZE only (fast, no cleanup)
ANALYZE;
ANALYZE orders (customer_id, order_date);   -- specific columns

-- REINDEX
REINDEX TABLE customers;
REINDEX INDEX idx_orders_customer;
REINDEX DATABASE mydb;
REINDEX SCHEMA public;

-- CONCURRENTLY — no write locks (PG12+)
REINDEX INDEX CONCURRENTLY idx_orders_customer;
REINDEX TABLE CONCURRENTLY customers;

-- From command line
vacuumdb -a -z              # all DBs with analyze
vacuumdb -j 4 -d mydb       # parallel (4 workers)

Autovacuum — الصيانة التلقائيةAutovacuum — Automatic Maintenance

Autovacuum خلفية تراقب الجداول باستمرار وتشغل VACUUM/ANALYZE تلقائياً. لا تعطلها أبداً في الإنتاج.

Autovacuum is a background process that monitors tables and runs VACUUM/ANALYZE automatically. Never disable it in production.

-- Key parameters (postgresql.conf):
-- autovacuum = on                                -- NEVER disable!
-- autovacuum_max_workers = 3                     -- increase for big DBs
-- autovacuum_naptime = 1min                      -- check every minute
-- autovacuum_vacuum_threshold = 50               -- min dead rows
-- autovacuum_vacuum_scale_factor = 0.2           -- 20% of table
-- autovacuum_analyze_threshold = 50
-- autovacuum_analyze_scale_factor = 0.1          -- 10% of table

-- Trigger formula:
-- vacuum when n_dead_tup > threshold + scale_factor × n_live_tup

-- For HOT tables (e.g., session tables) — more aggressive
ALTER TABLE user_sessions SET (
  autovacuum_vacuum_scale_factor = 0.02,     -- at 2%
  autovacuum_analyze_scale_factor = 0.01,    -- at 1%
  autovacuum_vacuum_cost_delay = 0           -- don't throttle
);

-- Monitor autovacuum activity
SELECT schemaname, relname,
       last_autovacuum, autovacuum_count,
       last_autoanalyze, autoanalyze_count,
       n_tup_ins, n_tup_upd, n_tup_del, n_dead_tup
FROM pg_stat_user_tables
ORDER BY last_autovacuum DESC NULLS LAST
LIMIT 20;

-- Currently running autovacuum workers
SELECT pid, datname, query
FROM pg_stat_activity
WHERE backend_type = 'autovacuum worker';
نصيحة للجداول الضخمة: Tip for huge tables: جدول 1TB مع scale_factor=0.2 لن يُفحص إلا بعد 200GB dead! خفضها إلى 0.02 (2%) للجداول الكبيرة. A 1TB table with scale_factor=0.2 won't vacuum until 200GB dead! Lower to 0.02 (2%) for big tables.

Transaction ID Wraparound — الكابوسTXID Wraparound — The Nightmare

TXIDs في PostgreSQL أرقام 32-bit. بعد ~2 مليار transaction، تبدأ الدورة. إذا لم يتم "تجميد" الصفوف القديمة، قاعدة البيانات تتوقف عن قبول الكتابة!

TXIDs in PostgreSQL are 32-bit. After ~2 billion transactions they wrap. If old rows aren't "frozen", the DB refuses writes!

الحادثة الشهيرة: The famous incident: Sentry (٢٠١٥) تعطل ٨ ساعات بسبب wraparound — منذ ذلك الحين Autovacuum يعمل FREEZE تلقائياً. Sentry (2015) had an 8-hour outage from wraparound — since then autovacuum runs FREEZE automatically. 
-- Monitor wraparound risk
SELECT datname,
       age(datfrozenxid) AS xid_age,
       ROUND(100.0 * age(datfrozenxid) / 2000000000, 2) AS pct_to_wraparound
FROM pg_database
ORDER BY xid_age DESC;

-- Alert thresholds:
--   > 50% → warning
--   > 75% → critical
--   > 90% → EMERGENCY — database will soon refuse writes!

-- Per-table age
SELECT c.relname,
       age(c.relfrozenxid) AS xid_age,
       pg_size_pretty(pg_total_relation_size(c.oid)) AS size
FROM pg_class c
WHERE c.relkind = 'r' AND c.relnamespace > 16384
ORDER BY age(c.relfrozenxid) DESC
LIMIT 20;

-- Force freeze on a table (when emergency)
VACUUM FREEZE big_old_table;

-- Related autovacuum params:
-- autovacuum_freeze_max_age = 200000000  (triggers "emergency" freeze)
-- vacuum_freeze_min_age = 50000000
-- vacuum_freeze_table_age = 150000000

Bloat — العدو الصامتBloat — The Silent Enemy

Bloat = مساحة مهدرة في الجداول/الفهارس. يحدث عند UPDATE/DELETE كثير بدون VACUUM كافٍ.

Bloat = wasted space in tables/indexes. Happens with heavy UPDATE/DELETE without enough VACUUM.

-- Simple bloat estimate (from pg_stat_user_tables)
SELECT relname,
       pg_size_pretty(pg_total_relation_size(relid)) AS size,
       n_live_tup, n_dead_tup,
       ROUND(100.0 * n_dead_tup / NULLIF(n_live_tup, 0), 2) AS dead_pct
FROM pg_stat_user_tables
WHERE n_dead_tup > 10000
ORDER BY n_dead_tup DESC
LIMIT 10;

-- Fix bloat approaches (no downtime):
-- 1. Run VACUUM regularly (autovacuum handles 90%+)

-- 2. pg_repack extension (re-pack without blocking!)
-- Install: CREATE EXTENSION pg_repack;
-- $ pg_repack -d mydb -t orders

-- 3. CLUSTER + re-create indexes (heavy lock!)
CLUSTER orders USING idx_orders_date;

-- 4. For index bloat
REINDEX INDEX CONCURRENTLY idx_name;   -- PG12+
