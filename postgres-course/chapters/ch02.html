الصورة الكبيرةThe Big Picture

PostgreSQL هو Client/Server يعمل بنموذج Process-per-Connection. عند بدء الخادم، عملية واحدة تُسمى postmaster تبدأ وتُدير كل شيء.

PostgreSQL is a client/server system using a process-per-connection model. On startup, a single postmaster process initializes and manages everything.

Backend ProcessesBackend Processes

عملية لكل اتصال — كل استعلام ينفذ داخل الـ backend الخاص به.

One per connection — each query runs in its own backend.

Background ProcessesBackground Processes

عمليات مساعدة دائمة (Checkpointer، Writer، Autovacuum...).

Persistent helpers (Checkpointer, Writer, Autovacuum...).

Shared MemoryShared Memory

Shared Buffers و WAL Buffers — مشتركة بين كل العمليات.

Shared Buffers & WAL Buffers — shared across all processes.

قاعدة ذهبية: Golden rule: عند رؤية أي سطر postgres: في ps aux، هذا إما postmaster أو backend أو utility process. كلها نفس البرنامج ولكن بأدوار مختلفة. Any postgres: line in ps aux is either postmaster, a backend, or a utility process. Same binary, different roles.

القسم ٣Section 3

معمارية الذاكرةMemory Architecture

Shared MemoryShared Memory

مشتركة بين كل العمليات — تُحجز عند startup.

Shared across all processes — allocated at startup.

  • shared_buffers: cache لصفحات الجداول: table page cache
  • wal_buffers: buffer مؤقت لسجلات WAL: temporary buffer for WAL records
  • CLOG: حالات الـ transactions: transaction statuses
  • Lock space: جدول الأقفال: lock table

Local MemoryLocal Memory (per backend)

خاصة بكل backend — مستقلة.

Private per-backend — isolated.

  • work_mem: للفرز والـ hash: for sort/hash operations
  • maintenance_work_mem: VACUUM، CREATE INDEX: VACUUM, CREATE INDEX
  • temp_buffers: للجداول المؤقتة: for temporary tables
احسب الذاكرة الكلية: Total memory calculation:
Total ≈ shared_buffers + (max_connections × (work_mem + temp_buffers)) + wal_buffers

حذّر! work_mem يُحجز لكل عملية sort في الاستعلام، فاستعلام بثلاث sorts يستهلك 3 × work_mem!

Warning! work_mem is allocated per-sort — a query with 3 sorts uses 3 × work_mem!

القسم ٤Section 4

WAL — قلب PostgreSQL النابضWAL — PostgreSQL's Beating Heart

WAL (Write-Ahead Logging) هو المبدأ: "اكتب التغيير في السجل قبل تطبيقه على البيانات". كل UPDATE/INSERT/DELETE يُكتب أولاً في WAL (فقط سجل صغير يصف التغيير) ثم يُطبق لاحقاً على ملفات البيانات.

WAL (Write-Ahead Logging) rule: "log the change before applying it to data". Every UPDATE/INSERT/DELETE is first written to WAL (a small record describing the change), then applied to data files later.

لماذا WAL؟ 3 فوائد كبرى:Why WAL? 3 Big Benefits:

  1. الحماية من الأعطال: عند crash، الـ WAL يُعاد تنفيذه (replay) لاستعادة البيانات.
  2. Crash safety: on crash, WAL is replayed to recover data.
  3. الأداء: WAL هو كتابة متتابعة (sequential) أسرع بكثير من الكتابة العشوائية على ملفات البيانات.
  4. Performance: WAL is sequential writing — much faster than random data file writes.
  5. النسخ المتماثل: الـ replicas تأخذ WAL وتطبقه (Streaming Replication).
  6. Replication: replicas receive WAL and apply it (Streaming Replication).
تحذير: Warning: لا تحذف ملفات pg_wal يدوياً! حتى لو امتلأ القرص — استخدم pg_archivecleanup أو أصلح archive_command. الحذف اليدوي = فقدان بيانات. Never delete pg_wal files manually! Even if disk fills — use pg_archivecleanup or fix archive_command. Manual deletion = data loss.
القسم ٥Section 5

MVCC — سر الأداء المتزامنMVCC — The Concurrency Secret

MVCC (Multi-Version Concurrency Control) يعني: بدل قفل الصفوف، PostgreSQL يحتفظ بنسخ متعددة من كل صف. كل transaction يرى "snapshot" يتطابق مع لحظة بدايته.

MVCC means: instead of locking rows, PostgreSQL keeps multiple versions of each row. Each transaction sees a "snapshot" matching its start time.

الفوائد Benefits

  • • القراءة لا تحجب الكتابة والعكس
  • • Reads don't block writes, and vice versa
  • • Consistency دون أقفال ثقيلة
  • • Consistency without heavy locking
  • • أداء ممتاز في أحمال OLTP الكبيرة
  • • Great performance on heavy OLTP

التكلفة Cost

  • • نسخ قديمة (Dead Tuples) تتراكم
  • • Old versions (dead tuples) accumulate
  • • VACUUM مطلوب بانتظام للتنظيف
  • • VACUUM needed regularly to clean up
  • • استهلاك مساحة قرص أعلى
  • • Higher disk usage

مثال عملي على MVCC:Practical MVCC example:

تبدأ User A باستعلام SELECT طويل على جدول. في الوقت نفسه، User B يعمل UPDATE على نفس الصفوف. Postgres يسمح للاثنين بالعمل في وقت واحد — User A يرى البيانات القديمة، User B يكتب النسخة الجديدة. لا أحد ينتظر!

User A runs a long SELECT. At the same moment, User B runs UPDATE on the same rows. PostgreSQL lets both proceed concurrently — User A sees the old data, User B writes the new version. No one waits!

القسم ٦Section 6

معالجة الاستعلام — ٥ مراحلQuery Processing — 5 Stages

1
Parser
يحول SQL النصي إلى parse tree — يتحقق من صحة البنية فقط (syntax).
Converts SQL text into parse tree — validates syntax only.
2
Analyzer
يتحقق من وجود الجداول، الأعمدة، الأنواع. يحوّل الـ parse tree إلى query tree.
Checks tables, columns, types exist. Converts parse tree to query tree.
3
Rewriter
يطبق قواعد الـ Views و Rules — مثلاً استعلام على view يتحول لاستعلام على الجدول الأصلي.
Applies view/rule transformations — e.g., view query becomes base-table query.
4
Planner / Optimizer
يختار أفضل خطة تنفيذ بناءً على الإحصائيات (من ANALYZE). قد يستخدم Seq Scan، Index Scan، Hash Join، Nested Loop، إلخ.
Picks best execution plan using statistics (from ANALYZE). May use Seq Scan, Index Scan, Hash Join, Nested Loop, etc.
5
Executor
ينفذ الخطة خطوة خطوة، يقرأ من shared_buffers أو القرص، ويرجع النتائج للعميل.
Executes the plan step by step, reads from buffers or disk, returns results.
القسم ٧Section 7

هيكلة مجلد البيانات PGDATAData Directory Layout (PGDATA)

$PGDATA/
├── base/                # One subdirectory per database (by OID)
│   └── 16384/           # e.g., database "mydb" — actual table files here
├── global/              # Cluster-wide tables (pg_database, pg_authid...)
├── pg_wal/              # Write-Ahead Log files (16 MB each)
├── pg_xact/             # Transaction commit/abort status (CLOG)
├── pg_multixact/        # Multi-transaction status (row locking)
├── pg_stat/             # Permanent stats files
├── pg_stat_tmp/         # Runtime stats (written by stats collector)
├── pg_subtrans/         # Subtransaction status
├── pg_twophase/         # Prepared transactions (2PC)
├── pg_tblspc/           # Symlinks to external tablespaces
├── pg_snapshots/        # Exported transaction snapshots
├── postgresql.conf      # Main configuration
├── postgresql.auto.conf # ALTER SYSTEM writes here (overrides conf)
├── pg_hba.conf          # Host-based authentication rules
├── pg_ident.conf        # OS username ↔ DB username mapping
├── postmaster.pid       # PID file (prevents double-start)
└── PG_VERSION           # Single integer: 18
معلومة عملية: Practical tip: داخل base/<oid>/ ستجد ملفات مرقمة. كل ملف = جدول أو فهرس. الرقم هو OID. استخدم SELECT oid, relname FROM pg_class لتعرف الملف الخاص بأي كائن. Inside base/<oid>/ you'll find numbered files — each is a table or index. Use SELECT oid, relname FROM pg_class to map files to objects.

TOAST: TOAST: لما يكون صف أكبر من 8 KB، PostgreSQL يستخدم TOAST (The Oversized-Attribute Storage Technique) — يضغط البيانات الكبيرة ويحفظها في جدول جانبي. When a row exceeds 8 KB, PostgreSQL uses TOAST — compressing large data and storing it in a side table.
